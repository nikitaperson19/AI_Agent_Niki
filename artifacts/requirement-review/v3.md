## Scope

Форма авторизации (Login Form) и связанная серверная логика входа:

- UI-состав формы: поля «Логин»/«Пароль», плейсхолдеры, маска, кнопка-иконка «глаз», кнопка «Войти», ссылки, чекбокс «Запомнить меня» (AUTH-001…006);
- клиентская валидация: заполненность, формат логина, нормализация (AUTH-007…009);
- серверная аутентификация: успех, неверные данные, блокировка при переборе (AUTH-010…012).

**Вне Scope по тексту требований:** регистрация, восстановление пароля (только ссылки), logout, смена пароля, NFR.

## Summary

**Общая оценка:** требования детализированы (точные regex, форматы телефона, лимиты, тексты сообщений, семантика счётчиков, cookie, open redirect). Большинство формулировок проверяемы. Однако есть несколько критических пробелов и конфликтов, из-за которых часть требований нельзя однозначно декомпозировать и покрыть тестами.

**Ключевые проблемы (кратко):**

1. Лимиты длины логина (≤254) и пароля (8–128) заданы, но поведение и текст ошибки при их нарушении отсутствуют; AUTH-004 перечисляет только AUTH-007/AUTH-008 как клиентские ошибки.
2. Конфликт AUTH-011 / AUTH-012 на пятой неудачной попытке (сообщение и сохранение пароля).
3. AUTH-010 декларирует защиту от open redirect, но не задаёт правил валидации return-URL.
4. AUTH-012 не определяет источник «IP-адреса клиента» (proxy/CDN, XFF, IPv6, NAT).
5. Не определено соотношение блокировки (AUTH-012) и клиентской валидации (AUTH-004) при блокировке + пустых полях.
6. Конфликт AUTH-001 («пробельные символы в логине допустимы») и email-regex AUTH-008, запрещающей `\s`.
7. AUTH-009 не самодостаточно («по существу без изменений»).
8. Не описано поведение при серверных сбоях (5xx, таймаут, сеть).

**Статистика:** 12 требований; 17 Ambiguities; 13 Missing Information; 4 Conflicts; 13 Risks; 16 Open Questions; 5 Escalations.

**Готовность к следующим этапам:** FAIL. Готовы 2 требования (AUTH-002, AUTH-005), частично — 8, заблокированы — 2 (AUTH-009, AUTH-010). Критические блокеры — в Escalations.

## Requirements

| ID | Формулировка (сжато, по тексту страницы) | Source |
|----|------------------------------------------|--------|
| REQ-AUTH-001 | Поля «Логин» (email или телефон, тип по наличию «@»), «Пароль». Логин ≤254 символа; пароль 8–128 символов Unicode, любые печатные символы включая пробел внутри. Обрезка пробелов только в логине; пароль не изменяется. Пусто после обрезки → незаполнено (AUTH-007). Пробелы внутри логина допустимы (игнорируются валидацией телефона). | §1 |
| REQ-AUTH-002 | Плейсхолдеры «Введите Email или телефон», «Введите пароль». Пароль маскируется `•`; при активном режиме видимости (AUTH-003) маскировка отключается. | §1 |
| REQ-AUTH-003 | Кнопка-иконка «глаз» (`aria-label`); клик и Enter переключают видимость, иконка меняется на «глаз перечёркнут». Видимость сбрасывается при полной перезагрузке и при любом неуспешном сабмите (AUTH-007/008/011/012). | §1 |
| REQ-AUTH-004 | Кнопка «Войти» активна всегда. Сабмит по клику и по Enter в любом поле. При клиентских ошибках запрос не отправляется, показываются AUTH-007/008, фокус на первое поле с ошибкой. Во время запроса — состояние загрузки, повторные нажатия игнорируются. При активной блокировке кнопка активна, но сабмит возвращает сообщение о блокировке без аутентификации. | §1 |
| REQ-AUTH-005 | «Забыли пароль?» → `/password-recovery`; «Зарегистрироваться» → `/registration`. | §1 |
| REQ-AUTH-006 | Чекбокс «Запомнить меня», по умолчанию снят. Cookie сессии только при успешном входе: отмечен → persistent 30 календарных дней от входа; снят → session cookie до закрытия браузера. Значение чекбокса между сессиями не запоминается. | §1 |
| REQ-AUTH-007 | Валидация заполненности при сабмите (включая Enter) и при blur поля, которое было заполнено и очищено. Пустое (после обрезки) поле: красная рамка + «Поле обязательно для заполнения». Ошибка снимается при вводе любого символа в это поле. | §2 |
| REQ-AUTH-008 | Формат логина — при blur (только непустое) и при сабмите. Email regex `^[^@\s]+@[^@\s]+\.[^@\s]{2,}$`. Телефон `+7XXXXXXXXXX` / `8XXXXXXXXXX` (10 цифр после префикса); пробелы, дефисы, скобки игнорируются. Иначе — красная рамка + «Некорректный формат email или телефона». Ошибка снимается при изменении значения. | §2 |
| REQ-AUTH-009 | «По существу без изменений»: email → нижний регистр, телефон → `+7XXXXXXXXXX` перед проверкой в БД; значение в поле не меняется; пароль сравнивается с учётом регистра. | §2 |
| REQ-AUTH-010 | При совпадении: аннулируется предыдущая сессия пользователя, создаётся новая, cookie HttpOnly/Secure/SameSite=Lax со сроком из AUTH-006, редирект на сохранённый return-URL того же домена (защита от open redirect), иначе `/account`. Сбрасываются оба счётчика AUTH-012 (по нормализованному логину и по IP). | §3 |
| REQ-AUTH-011 | Логин не найден или пароль не совпал → общее уведомление над формой «Неверный логин или пароль» без уточнений. Значения полей сохраняются, видимость пароля сбрасывается. | §3 |
| REQ-AUTH-012 | Неудачная попытка = сабмит, получивший ответ AUTH-011 (включая несуществующие логины). Клиентские ошибки и попытки во время блокировки счётчики не увеличивают. Два счётчика за скользящее окно 3 минуты: по IP и по нормализованному логину; одна неудача увеличивает оба. 5 неудач по любому счётчику → блокировка 15 минут от пятой попытки (по IP — любые логины с этого IP; по логину — этот логин с любого IP). Во время блокировки каждый сабмит: «Превышено число попыток входа. Попробуйте через 15 минут» без таймера, единая формулировка. Поля сохраняются, пароль очищается, видимость сбрасывается. Повторные попытки блокировку не продлевают. После снятия счётчики с нуля. | §3 |

**Примечание:** AUTH-001, -003, -004, -010, -012 — составные (один ID покрывает несколько независимых правил) → влияет на трассируемость и декомпозицию.
