## Задача 1: UI-компоненты формы авторизации

| Поле | Значение |
|------|----------|
| **Local ID** | TASK-001 |
| **Summary** | Реализовать UI-компоненты формы авторизации |
| **Description** | Реализовать форму авторизации со следующими элементами:<br><br>1. Поле ввода «Логин» (обязательное, текстовое) с плейсхолдером «Введите Email или телефон».<br>2. Поле ввода «Пароль» (обязательное, с маской скрытия символов) с плейсхолдером «Введите пароль».<br>3. Интерактивная иконка «глаза» для переключения видимости пароля (меняет состояние при нажатии).<br>4. Кнопка действия «Войти» — неактивна (disabled), пока не заполнены оба поля.<br>5. Кликабельные ссылки: «Забыли пароль?» и «Зарегистрироваться».<br>6. Чекбокс «Запомнить меня» (по умолчанию снят). |
| **Source Requirements** | REQ-AUTH-001, REQ-AUTH-002, REQ-AUTH-003, REQ-AUTH-004, REQ-AUTH-005, REQ-AUTH-006 |
| **Acceptance Criteria** | 1. Форма содержит ровно два обязательных текстовых поля: «Логин» и «Пароль».<br>2. Поле «Логин» отображает плейсхолдер «Введите Email или телефон».<br>3. Поле «Пароль» отображает плейсхолдер «Введите пароль» и скрывает вводимые символы (точками/звёздочками).<br>4. Иконка «глаза» переключает видимость пароля при нажатии; иконка изменяет своё состояние.<br>5. Кнопка «Войти» отображается, но неактивна (disabled), пока оба поля пусты.<br>6. Кнопка «Войти» становится активной после заполнения обоих полей.<br>7. Ссылки «Забыли пароль?» и «Зарегистрироваться» присутствуют и кликабельны.<br>8. Чекбокс «Запомнить меня» присутствует и по умолчанию снят. |
| **Dependencies** | Нет |
| **Priority** | HIGH — базовая функциональность формы (все последующие задачи зависят от неё) |
| **Open Questions / Blockers** | OQ-008: Куда ведут ссылки «Забыли пароль?» и «Зарегистрироваться» — существующие ли это страницы?<br>OQ-004: Какое поведение чекбокса «Запомнить меня»? |

## Задача 2: Клиентская валидация формы авторизации

| Поле | Значение |
|------|----------|
| **Local ID** | TASK-002 |
| **Summary** | Реализовать клиентскую валидацию полей формы авторизации |
| **Description** | Реализовать валидацию на стороне клиента:<br><br>1. При попытке отправки пустой формы — подсветить незаполненные поля красным цветом и вывести текст ошибки «Поле обязательно для заполнения» под каждым пустым полем.<br>2. Проверить корректность формата логина (email regex или международный номер телефона). При несоответствии — вывести сообщение «Некорректный формат логина или телефона».<br>3. Логин приводится к нижнему регистру (lowercase) перед отправкой на сервер.<br><br>Валидация должна происходить при попытке отправки формы (нажатии кнопки «Войти»). |
| **Source Requirements** | REQ-AUTH-007, REQ-AUTH-008, REQ-AUTH-009 |
| **Acceptance Criteria** | 1. При нажатии «Войти» с пустыми обоими полями — оба поля подсвечены красным, под каждым сообщение «Поле обязательно для заполнения».<br>2. При нажатии «Войти» с пустым только одним полем — только это поле подсвечено красным с сообщением.<br>3. При вводе логина некорректного формата (не email и не номер телефона) — сообщение «Некорректный формат логина или телефона».<br>4. При вводе корректного email/телефона — ошибка формата не отображается.<br>5. Логин отправляется на сервер в нижнем регистре. |
| **Dependencies** | TASK-001 (UI-компоненты должны быть реализованы) |
| **Priority** | HIGH — критично для корректной обработки данных |
| **Open Questions / Blockers** | OQ-005: Какие форматы международного номера телефона поддерживаются?<br>OQ-006: Есть ли ограничения на длину полей?<br>BLOCKED-001: Отсутствие спецификации формата телефона (MISS-002) — невозможность однозначной реализации валидации телефона. |

## Задача 3: Серверная логика аутентификации

| Поле | Значение |
|------|----------|
| **Local ID** | TASK-003 |
| **Summary** | Реализовать серверную логику аутентификации пользователя |
| **Description** | Реализовать серверный эндпоинт/обработчик аутентификации:<br><br>1. Принять логин (приведённый к lowercase) и пароль от клиента.<br>2. Проверить наличие учётной записи в БД по логину (регистронезависимый поиск).<br>3. Проверить совпадение пароля (регистрочувствительная проверка).<br>4. При успешной аутентификации: создать пользовательскую сессию, установить HttpOnly cookie, перенаправить пользователя на целевую страницу.<br>5. При неверных учётных данных (логин не найден ИЛИ пароль не совпадает): вернуть общее сообщение «Неверный логин или пароль» без указания, что именно неверно.<br>6. Интегрироваться с механизмом блокировки при переборе (TASK-004). |
| **Source Requirements** | REQ-AUTH-009, REQ-AUTH-010, REQ-AUTH-011 |
| **Acceptance Criteria** | 1. При валидной паре логин-пароль создаётся сессия и устанавливается HttpOnly cookie.<br>2. После успешного входа пользователь перенаправляется на целевую страницу.<br>3. При неверном пароле для существующего логина — сообщение «Неверный логин или пароль».<br>4. При несуществующем логине — сообщение «Неверный логин или пароль» (то же самое).<br>5. Поиск логина в БД регистронезависимый.<br>6. Проверка пароля регистрочувствительная.<br>7. Если аккаунт/IP заблокирован (TASK-004) — запрос отклоняется до истечения блокировки. |
| **Dependencies** | TASK-001, TASK-002 (UI + валидация), TASK-004 (механизм блокировки должен быть интегрирован) |
| **Priority** | HIGH — ключевая бизнес-функциональность |
| **Open Questions / Blockers** | OQ-002: Какой URL является целевым после успешного входа — главная страница или личный кабинет? |

## Задача 4: Защита от перебора (Brute Force Protection)

| Поле | Значение |
|------|----------|
| **Local ID** | TASK-004 |
| **Summary** | Реализовать механизм защиты от перебора паролей (блокировка при 5 неудачных попытках) |
| **Description** | Реализовать механизм временной блокировки:<br><br>1. Фиксировать неудачные попытки авторизации для каждого IP-адреса и для каждого логина.<br>2. При превышении 5 подряд неудачных попыток в течение 3 минут (по IP ИЛИ по логину) — временно заблокировать возможность входа для данного аккаунта/IP на 15 минут.<br>3. Во время блокировки выводить сообщение: «Превышено число попыток входа. Попробуйте позже через ХХ минут».<br>4. После истечения 15 минут блокировка автоматически снимается.<br><br>Требуется уточнение логики (см. Open Questions). |
| **Source Requirements** | REQ-AUTH-012 |
| **Acceptance Criteria** | 1. После 5 неудачных попыток за 3 минуты (с одного IP) — вход блокируется для этого IP.<br>2. После 5 неудачных попыток за 3 минуты (для одного логина) — вход блокируется для этого логина.<br>3. Заблокированный пользователь видит сообщение о превышении попыток.<br>4. Через 15 минут блокировка автоматически снимается, пользователь может повторить попытку.<br>5. Успешный вход сбрасывает счётчик неудачных попыток (требуется уточнение).<br>6. Сообщение о блокировке не раскрывает длительность блокировки точнее, чем указано в требованиях. |
| **Dependencies** | TASK-003 (интеграция с обработчиком аутентификации) |
| **Priority** | HIGH — безопасность |
| **Open Questions / Blockers** | OQ-001: Счётчики раздельные для IP и логина? Блокировка по любому критерию или обоим?<br>OQ-003: Сообщение статическое («15 минут») или динамическое (обратный отсчёт)?<br>BLOCKED-002: Неоднозначность логики блокировки (AMB-001) — требуется уточнение владельца требований. |
