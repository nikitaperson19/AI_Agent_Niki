# Task Design Skill

## Purpose

Skill преобразует проверенный **Requirement Review** в структурированный **Jira Tasks Artifact**, пригодный для последующего создания задач через Jira Tool.

> Skill проектирует **содержание** задач. Он **не выполняет** запись в Jira и **не управляет** Jira Tool напрямую.

---

## Inputs

### Обязательные входные данные

- валидный Requirement Review Artifact;
- Scope текущей задачи агента.

### Опциональные входные данные

- проектные правила декомпозиции задач;
- допустимые типы задач, если они заданы Context;
- приоритеты или ограничения, явно переданные агентом;
- релевантная информация о существующих задачах, если агент уже получил её через Jira Tool.

---

## Context Management

- Используй **Requirement Review** как основной Source of Truth для проектирования задач.
- Не возвращайся к полной истории чата, если необходимая информация уже содержится в валидном Requirement Review.
- Не используй существующие Jira-задачи как замену исходным требованиям.
- Если агент передал данные о существующих задачах — используй их **только** для предотвращения дублирования и согласования декомпозиции.
- **Не запрашивай Jira самостоятельно**: Tool-вызовы выполняются агентом согласно Agent Instruction.

---

## Procedure

1. Определи, какие подтверждённые требования требуют отдельной работы команды разработки.
2. Сгруппируй связанные требования в логически целостные задачи.
3. Разделяй задачи, если они имеют разные цели, разные критерии приемки, независимые риски или могут реализовываться отдельно.
4. Не дроби работу на задачи без самостоятельной ценности или проверяемого результата.
5. Для каждой задачи сформируй понятный **Summary**.
6. Сформируй **Description** на основании Requirement Review.
7. Добавь **Acceptance Criteria** только из подтверждённых требований или явно переданного проектного Context.
8. Сохрани **Traceability** к исходным требованиям (Source Requirements).
9. Укажи **зависимости** между задачами, если они следуют из Requirement Review.
10. Назначь **Priority** только если она может быть обоснована риском, бизнес-критичностью или явным Context; иначе оставь её неопределённой для агента или человека.
11. Выяви потенциальные **дубли** относительно информации о существующих Jira-задачах, если такая информация передана.
12. Сформируй **Jira Tasks Artifact**.

---

## Rules

- Не создавай задачу, если для неё нет основания в Requirement Review.
- Не добавляй Acceptance Criteria, которых нет в подтверждённых требованиях.
- Не разрешай бизнес-неоднозначности самостоятельно.
- Не смешивай в одной задаче независимые изменения без обоснованной причины.
- Не создавай несколько задач, описывающих одно и то же изменение.
- Не определяй Jira Project, Assignee, Sprint, Fix Version или другие проектные поля самостоятельно, если они не переданы Context.
- **Не вызывай Jira Tool.**
- **Не изменяй существующие Jira-задачи.**

---

## Reasoning Patterns

| Pattern | Описание |
|---------|----------|
| **Branching / Tree** | Может применяться, если существуют несколько существенно разных вариантов декомпозиции требований. Сформируй не более трёх вариантов, сравни их по атомарности, трассируемости, зависимости задач, риску дублирования и удобству реализации, затем выбери наиболее обоснованный. |
| **Self-Refine / Critic** | После формирования Jira Tasks Artifact проверь его по Completion Criteria. Исправь дубли, чрезмерно крупные задачи, потерю требований или необоснованные Acceptance Criteria. |

---

## Output

Создай **Jira Tasks Artifact**. Для каждой задачи укажи:

| Поле | Описание |
|------|----------|
| **Local ID** | Временный идентификатор (не Jira Issue Key). |
| **Summary** | Краткий и понятный заголовок задачи. |
| **Description** | Подробное описание задачи на основе требований. |
| **Source Requirements** | Ссылки на требования из Requirement Review, которые покрываются задачей. |
| **Acceptance Criteria** | Проверяемые критерии приемки. |
| **Dependencies** | Зависимости между задачами (если применимо). |
| **Priority** | Приоритет или признак, что Priority требует внешнего решения. |
| **Open Questions / Blockers** | Вопросы или блокировки, влияющие на создание задачи. |

> **Jira Issue Key** не должен присутствовать как фактически созданный, пока агент не выполнит Jira Tool и не получит подтверждение.

---

## Artifact Contract

| Параметр | Значение |
|----------|----------|
| **Producer** | Skill `task-design` |
| **Consumer** | Agent, этап создания задач через Jira Tool |
| **Artifact** | Jira Tasks |
| **Validation** | Completion Criteria этого Skill |
| **Error Handling** | Если Requirement Review содержит критическую неоднозначность, не позволяющую надёжно сформировать конкретную задачу — пометь соответствующую часть как **BLOCKED / REQUIRES_HUMAN_DECISION** вместо самостоятельного выбора. |

---

## Completion Criteria

- [ ] Каждая задача имеет основание в Requirement Review.
- [ ] Каждое значимое подтверждённое требование либо покрыто задачей, либо явно отмечено как не требующее отдельной задачи.
- [ ] Summary и Description понятны без повторного чтения всей истории агента.
- [ ] Acceptance Criteria не содержат придуманных бизнес-правил.
- [ ] Traceability к требованиям сохранена.
- [ ] Необоснованные дубликаты отсутствуют.
- [ ] Критические Ambiguities и Conflicts не скрыты.
- [ ] Artifact готов к передаче агенту для создания задач через Jira Tool.
