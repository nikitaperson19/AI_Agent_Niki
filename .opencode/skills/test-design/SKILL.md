# Test Design Skill

## Purpose

Skill проектирует **риск-ориентированную тестовую модель** на основании проверенного Requirement Review и формирует **Test Model Artifact**, пригодный для последующего создания тестовых сущностей через testomat.io Tool.

> Skill проектирует **тесты**. Он **не выполняет** тестирование и **не создаёт** сущности в testomat.io напрямую.

---

## Inputs

### Обязательные входные данные

- валидный Requirement Review Artifact.

### Опциональные входные данные

- ограничения тестирования;
- релевантные существующие тест-кейсы, если агент получил их через testomat.io Tool;
- проектные правила приоритизации;
- дополнительный Context, явно переданный агентом.

---

## Context Management

- Используй **Requirement Review** как основной вход для тест-дизайна.
- Не анализируй заново весь Confluence, если необходимая информация уже представлена в проверенном Requirement Review.
- Используй существующие тест-кейсы testomat.io **только** для анализа текущего покрытия и предотвращения дублирования.
- Не загружай в Context всю тестовую модель testomat.io, если достаточно релевантных тестов текущей функциональности.
- **Не вызывай testomat.io Tool самостоятельно**: Tool-вызовы выполняются агентом.

---

## Procedure

1. Определи тестируемые функции и бизнес-правила из Requirement Review.
2. Оцени риски и бизнес-критичность.
3. Определи **Positive Scenarios**.
4. Определи **Negative Scenarios**.
5. Покрой **Validation Rules**.
6. Покрой значимые **Boundary Conditions**.
7. Добавь важные альтернативные потоки и зависимости.
8. Используй **risk-based** подход для дополнительного покрытия рисков.
9. Для каждого сценария сформулируй проверяемый **Expected Result**.
10. Назначь **Priority** на основании риска и критичности.
11. Сохрани **Traceability** к Source Requirement.
12. Сравни с переданными существующими тестами и исключи необоснованные дубли.
13. Сформируй **Test Model Artifact**.
14. Проверь Artifact по Completion Criteria.

---

## Rules

- Не придумывай бизнес-поведение, которого нет в Requirement Review.
- Допускаются **risk-based** проверки, не описанные дословно в требованиях, но они должны быть явно обозначены как **QA/Risk-based**, а не как бизнес-требование.
- Каждый сценарий должен иметь понятную цель и проверяемый Expected Result.
- Не создавай несколько сценариев, проверяющих одно и то же без дополнительной ценности.
- Не скрывай нерешённые Ambiguities и Conflicts.
- **Не вызывай testomat.io Tool.**
- Не считай Test Model фактически созданной в testomat.io до подтверждения Tool на уровне агента.

---

## Reasoning Patterns

| Pattern | Описание |
|---------|----------|
| **Self-Refine / Critic** | Основной паттерн для проверки качества Test Model: Generate → Evaluate → Improve → Evaluate. Проверяй полноту покрытия, негативные сценарии, границы, ожидаемые результаты, приоритеты, трассировку и дубли. |
| **Branching / Tree** | Не применяется по умолчанию. Используй только если есть несколько существенно разных тестовых стратегий или вариантов покрытия, влияющих на риск, стоимость или время. Сравни не более трёх вариантов и выбери наиболее обоснованный. |
| **Reviewer** | Если Agent Workflow включает независимый Reviewer для критической Test Model — передай ему валидный Test Model Artifact и необходимые исходные ссылки, а **не** полную историю работы Skill. |

---

## Output

Создай **Test Model Artifact**. Для каждого тестового сценария укажи:

| Поле | Описание |
|------|----------|
| **Local ID** | Временный идентификатор сценария. |
| **Title** | Понятное название сценария. |
| **Source Requirement** | Ссылка на требование из Requirement Review. |
| **Priority** | HIGH, MEDIUM, LOW (или иной контракт, если задан). |
| **Type** | positive, negative, boundary, risk-based. |
| **Preconditions** | Предусловия (если применимо). |
| **Steps / Test Intent** | Шаги теста или краткое описание намерения. |
| **Expected Result** | Проверяемый ожидаемый результат. |
| **Risk Reference** | Ссылка на риск (если сценарий risk-based). |
| **Open Question / Blocker** | Вопрос или блокировка, если сценарий зависит от нерешённой неоднозначности. |

---

## Artifact Contract

| Параметр | Значение |
|----------|----------|
| **Producer** | Skill `test-design` |
| **Consumer** | Agent, этап создания тестовых сущностей через testomat.io Tool |
| **Artifact** | Test Model |
| **Validation** | Completion Criteria этого Skill |
| **Error Handling** | Если критическая часть требований неоднозначна — не выдумывай Expected Result; пометь зависимые сценарии как **BLOCKED / REQUIRES_HUMAN_DECISION** или исключи их из готовой к созданию части Artifact с явным объяснением. |

---

## Completion Criteria

- [ ] Критические подтверждённые требования имеют тестовое покрытие.
- [ ] Positive Scenarios покрыты.
- [ ] Релевантные Negative Scenarios покрыты.
- [ ] Validation Rules покрыты.
- [ ] Значимые Boundary Conditions покрыты.
- [ ] Expected Result определён для каждого готового сценария.
- [ ] Priority назначен или явно отмечено, что он требует внешнего решения.
- [ ] Traceability к требованиям сохранена.
- [ ] Risk-based сценарии отделены от бизнес-требований.
- [ ] Необоснованные дубликаты отсутствуют.
- [ ] Нерешённые Ambiguities и Blockers видимы.
- [ ] Artifact готов к передаче агенту для создания тестовых сущностей через testomat.io Tool.
